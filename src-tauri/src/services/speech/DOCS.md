# Speech service

Recording, transcription, and the retry path that keeps a failed voice note recoverable.

## Failure model

`SpeechError::Transcription` carries a `FailureKind`:

- **Transient** — 408, 429, 5xx, connect failures, timeouts, unparseable responses. Re-sent automatically.
- **Permanent** — 401/403, 4xx request rejections, missing API key, no speech detected. Never re-sent.

`retry.rs` runs at most `surfaces.speech_to_text.auto_retry_attempts` attempts (default 3, `1` disables retrying) with exponential backoff — 2s, 6s, 18s, capped at 60s, ±20% jitter. A numeric `Retry-After` header overrides the computed delay. Every intermediate failure emits `speech-transcription-retry`.

`transcribe_with_retry` takes an async callback (`on_retry`) that the loop awaits when an attempt fails and another is left, before the backoff starts. The automatic path uses it to report each failure in the pill or a toast, so a retry is reported when its attempt fails, not after the loop.

An optional abort (`watch::Receiver<bool>`) ends the loop with `SpeechError::Cancelled` (message `Cancelled`). It is checked before each attempt and raced against the request and the backoff sleep; a `true` aborts. A dropped sender never aborts. The automatic path passes an abort; a manual retry passes none and cannot be cancelled.

The HTTP timeout scales with payload size (`30s + bytes / 50 kB/s`, capped at 300s). A fixed ceiling turned slow uplinks into self-inflicted timeouts on multi-minute recordings.

## Audio clips

A recording is written to `audio_clips/<uuid>.wav` under the app data dir before the first transcription attempt, with a row in `audio_clips` (schema v6) holding the path, duration, and `expires_at`. Retention is `surfaces.speech_to_text.audio_retention_hours` (default 3, `0` disables storage entirely).

Lifecycle:

- **Success** — clip deleted immediately, unless `keep_audio_on_success` is set, in which case it is attached to the new history entry.
- **Failure** — a history entry is created with `success = false` and the clip is attached to it. This is the anchor for "Retry transcription" and "Export audio".
- **Cancelled recording** — Cancel while recording or paused keeps the samples: they are encoded and stored as a clip, and a failed entry "Voice note · m:ss — cancelled" (error `Cancelled`) holds it, so "Retry transcription" transcribes it later. Nothing is kept (no entry, no toast) when `audio_retention_hours` is `0`, the recording is shorter than `MIN_RECORDING_SAMPLES_SECS`, or encoding or storing the clip fails. The retention is read from the settings directly, so a missing STT model does not drop the audio.
- **Cancelled retry** — Cancel during an automatic retry creates the same failed entry with the clip attached, as the final failure does.
- **Expiry** — `spawn_audio_clip_sweeper` runs every 15 minutes (plus once at startup) and drops expired rows with their files.
- **Orphans** — the same sweep deletes any `.wav` no row points at. This is what reclaims clips lost to `ON DELETE CASCADE`, history retention pruning, and `clear()`; there is no file cleanup in the delete paths themselves.

Clips are on disk rather than in memory deliberately: a transcription usually fails because the network or the provider is down, and the user may well quit the app before trying again.

## Retry concurrency

`is_transcribing` guards the freshly recorded audio only. Manual retries use `SpeechService::begin_retry` / `end_retry`, a per-entry-id set, so replaying an hour-old clip never blocks a new recording and two retries of the same entry cannot overlap.

A manual retry **updates the history entry and the clipboard, and never pastes**. By the time someone retries, the app that had focus during dictation is long gone — pasting into whatever happens to be focused now would be worse than useless. For the same reason a retry does not re-run a pending skill, even if the original recording was started as "run skill with transcription".

A new recording stays blocked while an automatic retry runs: `is_transcribing` stays set until the loop ends or is cancelled.

`SpeechService::retry_abort` holds the abort sender of the running automatic transcription. It is armed in the callback of the first reported failure (so only a run that is retrying can be aborted) and disarmed after the loop returns. Before the first failure it is `None`.

Nothing is retried automatically at startup. Failed entries with a live clip wait for a click, which keeps the lifecycle free of a replay queue and avoids a burst of requests when the machine comes back online.

## Commands

The recording state machine lives in `session.rs`; `commands/speech.rs` wraps it (the audio-clip, recording-state and keyterms commands live there directly). `toggle_speech_recording` starts and stops (on stop it runs the retry loop in a background task); `cancel_speech_recording` has two branches: with `retry_abort` armed it only fires the abort (the transcription task then handles `SpeechError::Cancelled`), otherwise a recording or paused session is cancelled keeping its audio (ignored when not recording or while transcribing); `retry_transcription` spawns a background retry, drives the UI through events and returns immediately; `export_audio_clip` copies the WAV to a caller-supplied destination (the frontend picks it via `plugin-dialog`); `discard_audio_clip` deletes a clip before expiry. `get_audio_clip_info` returns `has_audio`, `expires_at`, `duration_secs`, `bytes` and `is_retrying` for one entry.

## Events

| Event | Payload | Emitted when |
|-------|---------|--------------|
| `speech-recording-started` | `{ action_id }` | Recording begins |
| `speech-recording-stopped` | `{ had_audio }` | Recording ends, before transcription |
| `recording-widget-state` | `{ state, level, elapsedMs, monochromatic }`, plus `attempt`, `maxAttempts`, `delayMs` when `state` is `retrying` | Every widget update (`state`: `recording`/`paused`/`processing`/`retrying`/`done`, `level` 0..1; `attempt` is the attempt about to run, `delayMs` the backoff before it); sent to the `recording-widget` window only |
| `speech-transcription-retry` | `{ attempt, max_attempts, next_in_secs, reason, entry_id }` | Each transient failure; `attempt: 0` marks the start of a manual retry |
| `speech-transcription-complete` | `{ text, duration_secs, entry_id }` | Success (or a discarded too-short recording) |
| `speech-transcription-error` | `{ message, recoverable, entry_id, has_audio, attempts }` | Attempts exhausted, a permanent failure, or a cancelled automatic retry (`message` `Cancelled`, `recoverable` = `has_audio`) |

Cancel of a recording emits `speech-recording-stopped` and then `speech-transcription-complete` with empty `text`, like a discarded too-short recording; when the audio is kept it also emits `history-changed` for the new entry and, when the pill was not shown, shows the toast "Recording cancelled — audio kept, transcribe from the menu".

Cancel of a retry emits no `speech-recording-stopped`; its `speech-transcription-error` follows `history-changed` and the toast (see "Recording widget").

`entry_id` is `null` for the automatic path when no history entry was created (pending-skill executions, no-speech results).

## Recording widget

Convention: the window pill (`src/windows/recording-widget/App.svelte`) and the GNOME Shell extension pill (`linux/gnome-shell-extension/promptheus@promptheus.desktop/extension.js`) look and behave the same (width, button order, icons, colours, gaps, hover, animations). A change to one pill's look or behaviour is made to both in the same change; only platform-forced differences are allowed and are listed under "macOS layout and dropdown".

`widget.rs` (`RecordingWidget`) is called from `session.rs` at every transition, so one place owns widget state and the setting check. Setting: `surfaces.speech_to_text.show_recording_widget`, default `true`; off keeps the toast-only behavior.

`appearance.icons` (`mono` default, shared with the notification icons): `mono` draws the "Copied" check of the `done` state in the widget foreground (`#e5e5e7`), `color` in green (`#62A878`). Read in `show()` with `show_recording_widget`, so a change applies from the next recording. GNOME: 4th argument of `ShowRecordingWidget`, the extension picks `icons/recording-check-mono.svg` or `icons/recording-check.svg`. macOS: `monochromatic` field of every `recording-widget-state` payload.

- **Transports** — GNOME Wayland: the extension draws the widget (`ShowRecordingWidget` / `UpdateRecordingWidget` / `HideRecordingWidget`, see [linux-wayland-gnome-extension.md](../../../../docs/gotchas/linux-wayland-gnome-extension.md)). macOS: webview window `recording-widget` (`src/windows/recording-widget/`) fed by `recording-widget-state`. The `retrying` state goes through its own call: GNOME `UpdateRecordingWidgetRetry(attempt, max_attempts, delay_ms)` (`update_recording_widget_retry`; `UpdateRecordingWidget` rejects `retrying`), macOS the `recording-widget-state` payload with `attempt`, `maxAttempts`, `delayMs`; `push` picks the call by the state. Any other Wayland session, or a failed `ShowRecordingWidget`, falls back to toasts for that recording with a `warn` log. On macOS the `recording-widget` window is re-classed at setup into the non-activating `NSPanel` subclass `PromptheusWidgetPanel` (`canBecomeKeyWindow`/`canBecomeMainWindow` NO, `hidesOnDeactivate` NO, `services/macos_panel.rs`), because a click on a plain `NSWindow` of an inactive app activates the app and the frontmost app stops receiving keystrokes; it is shown and hidden with tauri `show()`/`hide()`, never `show_panel_without_activating`.
- **Toasts** — while the widget is shown it replaces "Recording started", "Processing audio" and "Speech transcribed". Error and warning toasts and the reminder stay. A retry is reported in the pill, with no toast, while it is shown. Without the pill (setting off, fallback) each failure that leaves another attempt shows the warning toast "Retrying transcription" ("Attempt N of M failed — retrying in Ss"), once per failure; the final "Speech transcribed" toast then reads "Processed in X.Xs, attempt N of M" (without the attempt count when the first attempt succeeded). There is no toast after the loop. A cancel from the pill shows no toast, the pill closing is the confirmation. Without the pill a cancelled recording with kept audio shows the info toast "Recording cancelled — audio kept, transcribe from the menu" and a cancelled retry "Transcription stopped — audio kept, retry from the menu" ("Transcription stopped" when no clip is attached). A cancelled retry never shows a "Transcription error" toast.
- **Transitions** — `recording` ⇄ `paused` → `processing` → `done` (about 1 s, "Copied"), then closed. A failed attempt with another left moves `processing` → `retrying` (`retrying_if_current`, allowed only from `processing` or `retrying`) and each further failure re-enters `retrying` with the new values; a success after a retry goes `retrying` → `processing` (`processing_if_current`) → `done` or closed as above. X in `retrying` (action `cancel`) fires the abort, the `SpeechError::Cancelled` arm of the transcription task then closes the pill. The arm runs in this order: failed entry with the clip, `history-changed`, `close_if_current`, pending prompt cleared, info toast, `set_transcribing(false)`, `speech-transcription-error`. `retrying_if_current`, `processing_if_current` and `close_if_current` follow the generation guard below. `processing` shows only a dimmed wave of 2 px bars with 3 px gaps (the level meter's gap) across the inner width of the pill, travelling left to right once per 1.2 s: no buttons, no timer, no label. Bar count on both pills `floor((width − 2 × 14 + gap) / (bar + gap))` = 47. GNOME: driven by one `GLib.timeout_add` (33 ms), opacity 150. macOS: a staggered CSS `@keyframes` `scaleY` animation, color `#929294` instead of opacity. Closed without `done`: start failure (the recorder thread reports a stream build or play error, `start_recording` fails and the pill is never shown), too-short recording, encode or runtime/API-key error, transcription error, cancel, no speech detected. A pending skill closes the widget right after processing, with no `done`. The `done` row-1 content (check + "Copied") enters once with scale 0.85 → 1 and opacity 0 → 1, 180 ms, ease-out cubic, pivot at the centre; webview: CSS `@keyframes`, off under `prefers-reduced-motion: reduce`; GNOME: `ease` with `EASE_OUT_CUBIC` after the content is added to row 1.
- **Retrying** — row 1 shows the countdown text "Retry N/M in S s" (N the attempt about to run, S the whole seconds left, rounded up) at the left and the Cancel `X` at the right edge, in the 28 px action group. The renderer counts down from `delayMs` received once, with a timer that wakes at each whole-second change (GNOME: `widget.retryId`, a `GLib.timeout_add`; macOS: `setTimeout`). At 0 it replaces the text by a wave of 40 bars (`WIDGET_RETRY_WAVE_BAR_COUNT` / `RETRY_WAVE_BAR_COUNT` = `floor((264 − 2 × 14 − 28 − 10 + 3) / (2 + 3))`, the width left of the X, 2 px bars, 3 px gaps) travelling with the `processing` wave's 1.2 s period, while the attempt runs. - **Pause** — `is_recording` stays `true`; the cpal callback drops samples while paused and the microphone stays open (the OS indicator stays on); `SpeechService::elapsed()` excludes paused time; the reminder skips paused ticks and shifts its timers by the pause length. Stop from pause transcribes. In `paused` the meter bars hold the last level and are dimmed.
- **Level** — a session-scoped task every 50 ms computes the RMS of the new buffer tail (`reminder::rms`) and sends a level on a dB scale with state and elapsed time, awaiting each update before the next tick. `level_from_rms`: `dbfs = 20·log10(rms / 32768)`, level = `clamp((dbfs − FLOOR_DB) / (CEIL_DB − FLOOR_DB), 0, 1)` with `FLOOR_DB = −50`, `CEIL_DB = −20` (RMS ≈ 104 → 0, ≈ 1036 → 0.67, ≥ 3277 → 1). A linear `rms / 6000` kept normal speech (RMS 500–3000) at 0.1–0.4, so the bars looked flat. The mapped level then goes through `smooth_level`, an envelope follower stepped once per tick: `level += (target − level) · rate` with `LEVEL_ATTACK = 0.6` when the target is higher and `LEVEL_RELEASE = 0.2` when it is lower, so a rise reaches 60 % of the step in 50 ms and a fall from 1 to silence takes about 11 ticks (550 ms) to drop below 0.1. The smoothed value starts at 0 per session and is reset to 0 while paused. Rendering interpolates between the 20 Hz updates: GNOME calls Clutter `ease` on each bar's `scale_y` (a transform: sub-pixel, no relayout) with a 60 ms `LINEAR` ease, about one update interval, so successive segments join at a near-constant speed; the earlier 100 ms `EASE_OUT_QUAD` on `height` restarted at its highest speed every 50 ms and rounded to whole pixels, which showed as a slight tremor. Clutter computes the intermediate frames on the frame clock and JS runs only on the 20 Hz updates (see [linux-wayland-gnome-extension.md](../../../../docs/gotchas/linux-wayland-gnome-extension.md)); macOS bars are `transform: scaleY(…)` with `transition: transform 120ms ease-out`.

- **Pill skill run** — in the transcription task of `toggle_speech_recording`, `transcript_plan` picks the path from the pending target, the stop + chat flag and the transcript. Origin `ShiftClick` keeps the old path (pill closed at once, `speech-alternative-execute`, flag ignored). Origin `Pill` without the flag keeps the pill in `processing` and runs `run_skill_stream` in the backend (`run_pill_skill`): no-op `Channel`, transcript as `input_override`, source `pill`, route `clipboard`, `notify_success = false` (the pill's "Copied" replaces the success toast; the executor shows the error toast for prepare and stream errors). - **Stop + chat (`Chat` plan)** — with the flag the backend runs no skill and writes no clipboard: it adds the speech history entry (as dictation does, so the audio clip and `speech-transcription-complete` work the same), closes the pill (no `done`, no toast), snapshots the clipboard (`ClipboardService::fingerprint`, off the async runtime), stores it as a pending copy and opens the chat (`open_conversation_dialog`, source `pill`, `auto_send_input`, transcript as initial input, `copy_token`). The chat's frontend calls `copy_chat_answer_if_unchanged(token, text)` after the first answer; the answer is copied only if the clipboard still matches the snapshot.
- **Webview target delivery** — `ai_webview::send_to_provider_chat(app, provider_id, transcript)` (`provider_send.rs`) sends the transcript plus the pill context (context not cleared) to a provider webview in a new chat. The context goes as files: images `image-<number>.<ext>` (`number` = the pill number, `ext` from `media_type`, unknown → `png`) and, with text context, one `context.md` (`text/markdown`, holding `labelled_context()`); the message text is the transcript only. Order: `surface` (`SurfaceTarget::KeepActive`: creates or shows the host without changing the active tab), a new provider tab pushed (`arm_in_new_tab`; its child label picked), the message armed on that label, `activate_tab` creates the child, so the message is armed before its page loads. One new tab per run. A tab with an armed message is never unloaded by the live limit or the 30 min pass; if it is unloaded anyway (window hidden), its message goes to `fallback` at once. The pending message (`AiWebviewState::arm_message`) is delivered once, on the next `PageLoadEvent::Finished` whose host equals the provider URL host (`take_delivery`), by evaluating `delivery_script`. The page script `__deliverMessage` polls 15 s for the single selector `.ProseMirror[contenteditable="true"]`. `fetch` and `XMLHttpRequest.prototype.send` wrappers, installed once per document, count requests whose body is a `Blob`/`File` or a `FormData` with `Blob` entries (one per entry; not strings, `ArrayBuffer`, typed arrays or `keepalive`); a `fetch` leaves the count when its promise settles, an XHR on `loadend`. With files: arm the counter → paste each file as a named `File` in its own synthetic paste → wait (every 100 ms) until counted uploads ≥ number of pasted files, none in flight and 1 s with no new counted request → disarm → paste the transcript → synthetic Enter keydown every 500 ms until `location.pathname` matches `^/(chat|c)/` (sent) or 30 s pass (typed); no done within 20 s → text pasted, no Enter, `typed`. Runs without files skip the wait. It reports through router kind `webview_send_outcome` (`status=sent|typed|no_composer`, `run`, optional `uploads` and `waitedMs`; no text). Failure (outcome `typed`/`no_composer`, any surface or tab activation error, a replaced message, or no outcome within the 80 s deadline) → `fallback`: transcript to the clipboard inside `spawn_blocking` (never on the GTK main thread) and an always-shown error toast `Not sent to <provider>`. Reasons: synthetic Enter over a send button (localized labels, claude.ai's Enter handler sends during a running upload, so the script waits for the upload requests); the path check over "composer empty" (claude.ai turns a long paste into an attachment, so the composer can stay empty after a failed send).
- **Claude Desktop target delivery** — `claude_desktop::deliver(app, transcript)` (`claude_desktop/`), spawned by the route (`tauri::async_runtime::spawn`, not awaited, so `set_transcribing(false)` and `speech-transcription-complete` are not delayed). Order: `read_context` (`ai_webview`, context not cleared), placement, macOS only `claude_running()`, macOS only the Accessibility check (untrusted → `NoPermission` with no run files, no link and no pasteboard write), run files, `OpenerExt::open_url` of `claude://claude.ai/new?surface=chat&q=<encoded>`, then the platform paste. Placement (`LINK_TEXT_LIMIT` 14,336 UTF-16 units): with text context, the context in `context.md` and the transcript in `q`; transcript over the limit → context + `"\n\n"` + transcript in `context.md`, `q` empty; without context, the transcript in `q`, or in `context.md` with `q` empty over the limit. The fallback text is always the full text (context and transcript). Encoding: every UTF-8 byte outside `A-Z a-z 0-9 - . _ ~` becomes `%XX` (as Python `urllib.parse.quote(text, safe="")`), hand-written. Run files: process-wide run number from 1; images `image-<number>.<ext>` (`number` = the item's pill number, name from `read_context`; `ext` from `media_type`, unknown → `png`) and `context.md` go to `<app_cache_dir>/claude-desktop/<run>/` inside `spawn_blocking`; a write error is `Failed`. The run directory is removed 5 min after the outcome is acted on, and `<cache>/claude-desktop/` once at app start (`spawn_claude_desktop_cache_clear`). Outcome (`Sent`, `NoWindow`, `FocusLost`, `NoRead`, `NoPermission`, `Failed`; `Outcome::from_reply` maps `sent|no_window|focus_lost|no_read`, any other string → `Failed`, an error → `Failed`): `Sent` → nothing; `NoWindow`, `NoPermission`, `Failed` → `ai_webview::fallback` (full text, context and transcript, to the clipboard; error toast `Not sent to Claude Desktop`); `FocusLost`, `NoRead` → error toast `paste with Ctrl+V and press Enter` (`Cmd+V` on macOS), clipboard untouched. Logs (target `app_lib::services::speech::claude_desktop`): `info` run number, outcome name, file count, `cold`/`warm` on macOS only; `warn` for the failure reason, never user data. Linux: `linux::paste_into_claude` needs `is_gnome_wayland()`, then calls `ShellProxy::paste_into_app("com.anthropic.Claude", uris)` (`file://` URIs of the run files) on the tokio runtime, never the GTK main thread, up to ~30 s; a zbus error becomes `Failed` with its D-Bus error name. The macOS paste follows in its own bullet; the extension's `PasteIntoApp` (focus the window, save the clipboard, own it with the file list, Ctrl+V, Return, restore) is in [`docs/gotchas/linux-wayland-gnome-extension.md`](../../../../docs/gotchas/linux-wayland-gnome-extension.md).
- **Claude Desktop on macOS** — `claude_desktop/macos.rs`. `claude_running()` (before the link): `NSWorkspace` running applications contain `com.anthropic.claudefordesktop` → warm. `accessibility_trusted_or_prompt()` (before the link): `AXIsProcessTrustedWithOptions` with `kAXTrustedCheckOptionPrompt` = true (`extern` declarations linking `ApplicationServices`, options built as an `NSDictionary`, toll-free bridged to `CFDictionary`); when untrusted macOS shows its own Accessibility dialog and adds Promptheus to the Accessibility list unchecked, so the app opens no settings pane itself. The app is ad-hoc signed (`signingIdentity: "-"`), so macOS asks for Accessibility again after each rebuild.

## Settings agent destination

- `start_settings_agent_dictation` (mic button of the settings agent composer) starts a recording through `toggle_recording(app, None, true)`; a recording already running returns `AlreadyRecording`. After `start_recording` it calls `SpeechService::lock_settings_agent_target`: pending and taken target `__settings_agent__` / "Settings agent" (`SETTINGS_AGENT_ID`, `SETTINGS_AGENT_LABEL`) and `target_locked` set at start, so `select_target`, `request_stop_chat`, paste, screenshot and select text are refused (`TargetLocked`) for the session.
- `transcript_plan` returns `TranscriptPlan::SettingsAgent` for that target before any other arm, also with `stop_chat` requested. The plan closes the pill and emits `settings-agent-dictation { text }` to the `settings-dialog` window only; an empty transcript emits nothing. No clipboard write, paste, chat, skill run or history entry (`speech_output_route` is `None`).
- `PillModel.minimalIntents` is true when `selectedId` is `__settings_agent__`. Row 2 of both renderers is already the centred label only while `targetLocked`, so the session shows the label with Finish, pause and cancel in row 1 and no Stop + chat, paste, select text, screenshot or chevron; `minimalIntents` also holds that in the macOS renderer. Platform-forced difference: the `UpdateRecordingWidgetModel` D-Bus signature has no field for it, so the extension derives it from `selectedId` (`WIDGET_SETTINGS_AGENT_ID`).
