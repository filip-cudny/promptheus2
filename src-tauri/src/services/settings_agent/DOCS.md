# Settings agent

Proposes changes to the app settings; the user applies them. Files: `tools.rs` (tool definitions), `dispatch.rs` (`Dispatcher`, redaction of every tool result), `plan.rs`/`apply.rs`/`testing.rs` (plan, write, test rows; `testing::run_row_test` is the one row test function), `engine.rs` (session and tool loop), `mcp.rs` (`McpSource`, the MCP tools of the agent), `transcript.rs` (per-turn transcript file), `system_prompt.md`. Commands: `commands/settings_agent.rs`.

## Tools

`settings_read` (values, models, skills, skill, prompt, missing_env, env_vars, change_log), `settings_test` (validate and test operations, show nothing), `settings_propose_changes` (one card per request), `settings_secret` (`{name}`, strict: shows the user the current value of a listed variable as a read-only masked field with a reveal toggle in the messages; returns at once `{name, outcome}` with `shown` when `secrets::current_value` is non-empty, else `not_set` and nothing is shown; never waits and never changes a value, that is a `set_env_value` row; extra fields such as the old `purpose` are an `invalid arguments` error). Anything else is an error result, except the MCP tools the user enabled for the agent.

MCP tools (`mcp.rs`): `surfaces.settings_agent.generation.enabled_tools` (qualified `server.tool` names) is picked by the user in Settings ("Settings agent tools", `SurfaceToolsPicker`); `plan::set_setting` refuses that key with a row error keyed at it, so the agent cannot enable tools for itself. `McpSource` (`Send + Sync`) gives the definitions of the enabled names (`tools`: qualified name plus `rmcp::model::Tool`) and calls one by qualified name (`call`: text and an error flag); `RegistrySource` wraps the managed `Arc<McpRegistry>` and calls through `execution::stream::call_mcp_tool` (the chat's helper; a call error is `Error executing tool '<qualified name>': <error>`), tests use `ScriptedMcp`. `select_enabled` keeps the tools the model sees under their raw name, as the chat does: a tool whose raw name equals a settings tool name, and every tool sharing a raw name with another enabled tool, is dropped with a `warn` naming it. The `Dispatcher` maps raw name to qualified name for the kept tools; a call to any other name is the `unknown tool` error. Results and errors pass `Redactor` like every result. The `debug` log names the called tool, never arguments or result text. The tool list is read once per turn from the turn's settings, so a change in Settings applies from the next message. Servers are never started or restarted for the agent: a tool the registry does not hold (server failed to start, removed since) is left out, with the registry's `warn`.

The `operations` schema of `settings_test` and `settings_propose_changes` is typed (`tools::operation_schema`, built with `json!`): an item has `op` (`enum` of `Operation::NAMES`) and an `anyOf` with one branch per operation: `description`, `properties` (`op` as a one-value `enum`, the variant's fields, nested `model`, `config`, `provider`, `frontmatter` with their own `required`) and `required` exactly as serde requires it (`op` included; `#[serde(default)]` and `Option` fields optional). No `strict`, `const` or `oneOf` (OpenAI-compatible endpoints may reject them); the schema is guidance and `dispatch.rs` validates. `tools_tests.rs` keeps it in sync with `Operation`: the `op` enum equals `NAMES`, every variant has a branch, an object filled from a branch's `required` deserializes into that operation and fails without any one of them. A new operation or field is added to `Operation`, `NAMES` and the branch together. `NAMES` has 21 entries; `set_env_value` is the last.

`settings_read` `what: "change_log"` (`change_log_read.rs`, a pure function over the `load_all` entries of all hosts) takes optional filters, combined: `since`/`until` (RFC 3339, both inclusive, compared as times; an unparsable value is an error naming the field), `key` (a setting effect path starting with it, e.g. `models[a]`), `op`, `text` (case-insensitive in request, reply or an operation label), `host`, `limit` (default 20, clamped to 1..=100). The result is `{entries, more}` newest first, `more` = matching entries not returned, plus a `hint` (narrow by `until` = the oldest returned `created_at`, `key` or `since`) when `more > 0`. An item has `id`, `created_at`, `host`, `kind`, `state` (`applied` | `undone`, `entry_state` over all entries), `request`, `reply`, `undoes`, `operations: [{label, op, effects}]` (no test results); setting effects carry `path`, `before`, `after`, file effects the `path` only; a secret entry carries `secret: {name}` (no backup); a secret effect (`set_env_value`) reads `{"target": "secret", "name"}` and nothing else, in the list and by id. `name` = an entry id returns that entry whole (file effects with `before`/`after` content) or the error `change log entry '<id>' not found`, other filters ignored. Every literal `api_key` in an effect's `before`/`after` is replaced by `[redacted]` first (`REDACTED`): any object member named `api_key` at any depth (a deleted model, a removed-item `{index, value}`, a whole `models` list) and the whole value of an effect whose path ends with `.api_key`, unless the string is empty or exactly one `${VAR}`; `Redactor` knows only current keys and cannot cover a deleted model's key. A new effect shape that can hold a key is covered by that walk, not by `Redactor`.

`settings_read` and `settings_secret` are strict tools: both carry the `promptheus/strict` meta key (`tools::strict`) and `mcp_tool_to_payload` sends `"strict": true` for them in OpenAI Responses mode (see "AiService specifics" in `services/DOCS.md`). Their schemas follow the strict rules: `additionalProperties: false`, every property in `required`, every `settings_read` property except `what` typed `[<type>, "null"]` (the agent sends `null` for an unused one). `tools_tests.rs` checks this recursively. `settings_test` and `settings_propose_changes` stay non-strict: their `anyOf` schema cannot be strict without encoding maps as strings.

Argument errors are per row: `dispatch::parse_operations` parses `operations` as a list of values (a missing or non-array list is an `invalid arguments` error result) and each item alone. Every bad item becomes a row error `{row, key: null, message}`, all in one call, and nothing is planned until every row parses: an unknown or missing `op` names the given op and lists `NAMES`; any other failure reads `<op>: <serde message>; fields: <required>, optional: <optional>` (`tools::operation_fields`). Row errors, also those of `plan`, are an ordinary result (not `is_error`) with a `note`: nothing was proposed (`settings_test`: tested) and the whole corrected list must be sent again. Not-found plan errors list the valid names at that row's state (`models:`, `skills:` from `skills_order`, `variables:`; an unknown model reference lists the ids of the matching model type).

## Environment variable operations

`add_env_var`, `update_env_var`, `rename_env_var`, `delete_env_var` (`operations.rs`, arms in `plan::apply`) change `Settings::env_vars` and the `${VAR}` references as setting effects only; `.env` is never written in a plan (rename reads it). Errors are keyed `env_vars[<name>]` (`.name` for name problems).

- `set_env_value { name }` (label `Set value of <name>`) has no value field: the user types the value in the card and it travels as `values` of `settings_agent_apply`. The plan fails keyed `env_vars[<name>]` (`variable not found; variables: ...`) when `<name>` is not in `env_vars` at that row (an earlier `add_env_var` row counts); it changes no setting and returns one effect `Target::Secret { name }` with `before` and `after` `None`. `plan::mismatches` skips secret effects, so such a row is never stale and never an Undo conflict through `mismatches`. `apply::apply` writes the typed values (see "Secret guarantees" and `services/change_log/DOCS.md`, "Apply and undo").

- `rename_env_var` refuses when `new_name` already has a non-empty value on this machine that differs from the old name's (`secrets::current_value`); otherwise it renames the entry, sets `renamed_from` to the old name followed by the earlier ones (newest first, no duplicates, so `copy_renamed_values` takes the latest) and replaces every `${old}` token (exact token, also inside longer strings) in every field of `missing_env::visit_refs_mut`. MCP `env` keys are never touched, only values.
- `delete_env_var` fails with `used in: <labels>` while `collect_missing(settings, |_| false)` lists the name; a row earlier in the same plan that reassigns the reference lets it pass. It does not touch `.env`.
- `set_setting` refuses `env_vars` (`SETTINGS_MANAGED_BY_OTHER_OPERATIONS`).
- `set_setting` list-item keys: besides exact non-managed catalog keys it accepts a concrete key of `models` or `webview_providers` whose `catalog::catalog_path` is a catalog entry with `Applies::Live` (`models[<id>].store`, `webview_providers[<id>].name`); `models[<id>].id`, `webview_providers[<id>].id`, `mcp_servers.*`, `keymaps[...]` and `env_vars[...]` stay refused. The item must exist (`model '<id>' not found`, `web provider '<id>' not found`, keyed at the key); `models[<id>].api_key` takes a string that passes `check_api_key` (empty or one `${VAR}`). The write is `set_at`, the value check `catalog::check_changed`, the effect keyed by the concrete path, so apply and Undo are unchanged.
- Walker: `missing_env::visit_refs` (read, with key and label) and `visit_refs_mut` (`&mut String`) visit the same fields in the same order; `collect_missing` and rename use them, so a new field that may hold `${VAR}` is added there once.
- List key: list items are keyed in effect paths (`<list>[<key>]`) by `id`, `context` or `name` (`plan.rs::item_key`, `catalog.rs::collect_leaves`), so an effect on one `env_vars` entry is independent of the others and its Undo does not conflict with a later edit of another. A rename is a removal of `env_vars[old]` plus an addition of `env_vars[new]`; an apply appends the new entry at the end of the list, an Undo restores the old one at its position.
- Read: `settings_read` `what: "env_vars"` and the command `get_env_vars` (`commands/env_vars.rs`, fresh settings) return `missing_env::env_var_overview`: one `EnvVarStatus` per `Settings::env_vars` entry in list order with `name`, `description`, `secret`, `set` (value present on this machine, `env_is_set`), `value` and `used_in` (key and label of each field that references it, from `collect_missing(settings, |_| false)`). `value` (from `secrets::current_value`) is present only for a `secret: false` variable with a non-empty value and is omitted otherwise, so the agent reads plain values such as paths from `settings_read` while a secret's value never appears. Both callers pass the value lookup. An `update_env_var` row that switches `secret` from `true` (in the settings before the row) to `false` is labelled `Update variable <name> (value becomes visible to the agent)`.
- GUI: `apply_env_var_operation(operation)` (`commands/env_vars.rs`) accepts only these four, plans one operation with `plan::plan_single` (same `plan` as the agent) and writes a `Card` entry through `apply_plan` without request, reply or tests; it returns the entry id.

## Loop

`engine::run_turn(session, user_text, ctx, live)` appends the user message and loops up to `MAX_TOOL_LOOP_ITERATIONS`: `AiService::complete_stream(agent model, messages, Some(agent parameters), None, tools::definitions() plus the enabled MCP tools)`, `run_stream_loop`, `Dispatcher::dispatch` for each pending call in order, `build_tool_loop_messages` (which also carries the round's Responses reasoning items back into the next request). The final assistant text is `last_reply`. When the response of the last iteration (the 11th request) still has tool calls, they are not run: each is finished as failed with "not run: the agent reached the limit of 10 tool rounds" and the turn ends with the error `Stopped after 10 tool rounds without finishing.` plus ` Last tool error: <text>` when a tool result of the turn was an error (an `is_error` result's text, or the last row of a non-empty `errors` array as `row <n>: <message>`); the session keeps the messages up to the last dispatched round. Model: `surfaces.settings_agent.generation.model_id`, falling back to `surfaces.chat.generation.model_id` when it is `None` or empty; `complete_stream` gets `parameter_overrides` = the chat's `surfaces.chat.generation.parameters` merged with `surfaces.settings_agent.generation.parameters` (`ModelParameters::merged_with`): each parameter the agent leaves unset takes the chat's value, also when the agent model differs from the chat model. Neither model set ("no settings agent or chat model configured"), or an id `AiService` has no provider for ("model '<id>' is not available"), ends the turn with an error event before any request. The chosen id is logged at `debug` when the turn starts. System prompt: `system_prompt.md` plus the catalog `ENTRIES` as JSON; no Prompt Base. `EngineContext` has no `AppHandle` (settings snapshot taken at turn start, dirs, `AiService`, an `Emit` sink, an `McpSource`), so tests run it with `MockProvider` and a `LiveExecution` without channel.

## Session

One `Session` (`Arc<std::sync::Mutex<Session>>`, managed in `setup/state.rs`, never locked across an await): messages, `last_request`, `last_reply`, the current `proposal`, the cancel sender. In memory only: `settings_agent_reset` and the `Destroyed` event of the `settings-dialog` window (`services/dialog.rs`) reset it and cancel a running turn (a generation counter keeps a cancelled turn from writing back). One turn at a time. Each applied card keeps request and reply in its change-log entry.

## Transcript

Every turn leaves one JSON file in `<app_data_dir>/settings-agent-turns/` (`transcript.rs`; the dir of `history.db`, local, never synced; `EngineContext::transcript_dir`), named `<UTC YYYYMMDDTHHMMSSZ of the turn start>-<8 hex of a v4 uuid>.json`; the stem is the turn `id`. `run_turn` writes it once when the turn ends, on every end: reply, error (also before any request, and from inside `run_stream_loop`), cancel, loop limit. A write failure logs `warn` and does not change the outcome; `debug` logs the id and path, never content. The app log carries no user text, model text, tool arguments or results; the transcript is where they live.

Format (snake_case): `id`, `started_at`, `finished_at` (RFC 3339 UTC), `model_id` (null when none was found), `parameters` (the merged `ModelParameters` sent), `user_text`, `iterations: [{started_at, millis, text, thinking, reasoning_items, tool_calls: [{id, name, arguments, result, error, millis}]}]`, `end: {kind: "reply" | "error" | "cancelled" | "loop_limit", reply?, error?}`. An iteration is one provider request: `millis` is request start to end of stream, `text` is that round's own text (without the earlier rounds' prefix), `reasoning_items` a count (content is not stored). A tool call's `result` or `error` is the dispatched `result_text` (already through `Redactor`); calls not run at the loop limit carry the not-run text as `error`. A round cancelled during its request has no iteration. The end `error` passes `Redactor::new(config_dir, settings).redact` before it is stored; `user_text`, `arguments` and model text are stored as they are.

Pruning: `transcript::prune(dir, retention_days, now)` deletes files whose `started_at` is older than `history_retention_days` (0 deletes nothing; an unreadable file is skipped with `warn`). It runs at startup (`setup/state.rs`) and in `update_history_retention`, next to the change log prune.

## Events and commands

- Event `settings-agent-proposal { proposal_id, rows: [{ row, label, op, effects, test, waits_for, new_destination, stale, env_value }] }`; `waits_for` is the array of variable names the row waits for (empty when none), `new_destination` the text of a withheld automatic test or `null` (see "Row tests"); `env_value` is `null` except for a `set_env_value` row, where it is `{ name, secret, set }` (`secret` from the variable's entry in the plan's `env_vars`, `set` = `secrets::current_value` is non-empty; never a value); `row` is the 0-based operation index. `label` is `Operation::label` over the settings before that row (`plan::run_row`; the `settings_test` and `settings_propose_changes` results reuse it): a list-item `set_setting` key reads `<model display_name | provider name>: <catalog label>` (`Model abc: Store`), `delete_model` and `delete_webview_provider` name the item; an item not found shows its id. Stored change-log labels are not recomputed.
- Event `settings-agent-secret-view { name }`, emitted by `settings_secret` through `SessionSink` (a `SecretViewSink`; no emit after the turn was cancelled) only for outcome `shown`; the payload is the name and nothing else. The frontend attaches it to the running assistant message and renders a read-only `SecretField`, which loads the value itself with `get_secret_value`.
- `settings_agent_send(message, on_event)`, `_cancel`, `_reset`.
- `settings_agent_apply(proposal_id, selected, values)` (`values`: variable name to the typed value, camelCase arg `values`) returns `{ entry_id }`, `{ stale_rows }` or `{ error }` (no rows selected, dependency errors with row numbers, failed write). It plans with the selection, writes through `apply_plan` (097-04) with `last_request`, `last_reply`, the row tests and `values`, and clears the proposal. A selected `set_env_value` row without a non-empty value fails with `no value entered for <NAME>` before anything is written; a key of `values` with no selected `set_env_value` row is ignored.
- `settings_agent_reject(proposal_id)` drops the proposal and writes nothing.
- `settings_agent_refresh(proposal_id)` re-plans the same operations on the current settings and re-emits the proposal; row tests are kept.
- `settings_agent_test_row(proposal_id, row, values)` (`values`: variable name to the typed value, camelCase arg `values`) runs `run_row_test` for one row with the command's fresh settings as "before", the proposal's operations and plan, the given values and new destinations allowed. A tested result is stored in the proposal (the row's waits and new destination are cleared) and returned; a waits result is the error `row <n> waits for a value of <names>` (its destination text is dropped), a row without a test `row <n> has no test` (`<n>` the 0-based row).

## Row tests

`testing::run_row_test(&RowTestRequest)` is the only way a row is tested (no `AppHandle`; `Dispatcher::run_tests` and `settings_agent_test_row` both call it). The request carries the row index, all operations, the `Plan`, the settings before the plan, the staged `values`, the AI factory (`&(dyn Fn(&Settings) -> AiService + Sync)`), placeholders, the config dir and `allow_new_destinations` (`true` only from the card's test button). It returns `RowTest`: `NotTestable`, `Waits { names, new_destination }`, `NewDestination(text)` or `Tested(TestResult)`; `debug` logs the row index and the kind, never a value. Testable rows: `add_model`/`update_model`, `create_skill`/`update_skill` (on `skill_model_id`), `add_mcp_server`/`update_mcp_server`.

Order of checks:

1. Waits. The variables a row uses are the `${NAME}` references (`env_ref_names`) in the `visit_refs` fields of its item: `models[<id>].` for a model, `mcp_servers.<name>.` for an MCP server, the model a skill runs on for a skill (`Binding::variables`, over a settings holding only that item). A used `NAME` with a `set_env_value` row in the proposal and no non-empty entry in `values` makes the row wait: `Waits` lists those names sorted, each once, and nothing runs. A waiting row also carries the text of step 2 (`new_destination`, `None` when every destination is known), computed over the settings before the plan whatever `allow_new_destinations` says, so the card knows at propose time that typing the key would send it to a new destination.
2. Destination binding (a non-waiting row is checked only when `allow_new_destinations` is false). A model's destination is its `base_url`, or `<provider> default endpoint` (provider in its serde form, `openai default endpoint`) when empty; an MCP server's is its `command` as written. A variable's destination is known when the settings before the plan have an item of the same kind with the same destination whose references include that variable; the exception is a model on its provider's default endpoint (`base_url` `None` or empty), known for any variable, also one added in the same card (register #85: it reaches the provider's official host, never a custom host; accepted that a key can reach another provider's official endpoint). Every used variable with an unknown destination makes the result `NewDestination("test on click: <VAR> goes to new destination <destination>")` (several joined by `; `); no factory call, no MCP start. The reason: `ai/http.rs` sends a model key as `Authorization` to any `base_url` and an MCP test starts the `command`, so an automatic test must not hand a key to a destination the user has not seen.
3. Test. The settings of the plan are cloned and every `${NAME}` token of a non-empty staged value is replaced by the value in every `visit_refs_mut` field; the factory builds the `AiService` from that clone and the model, skill or MCP test runs on the clone's item. `set_override` and `.env` are never touched. The `TestResult` `error` and `output` pass `Redactor::new(config_dir, plan settings).with_values(staged values)`, so a provider error echoing a staged value returns `[redacted]`.

`Dispatcher::run_tests` calls it for every row with empty `values` and new destinations not allowed. `Proposal` keeps `tests`, `waits` and `new_destinations` per row index; `settings_test` and `settings_propose_changes` return per row `waits_for` and `new_destination` next to `test`. The agent therefore sees a row without a test until the user enters the value or clicks the test button. The card re-tests a waiting row automatically on key entry only when its `new_destination` is `null`; a row with a destination text waits for the test button.

Limit: item variables are found over a settings holding only that item, so a model or server name is never confused with another; a variable in a field `visit_refs` does not visit (none today) is neither waited for nor bound to a destination until it is added there.

## Secret guarantees

A secret value never enters a provider request: the agent never receives one (redacted settings, `${VAR}` references; `settings_secret` returns an outcome only and its event carries the name only; the one value the agent reads is that of a variable listed with `secret: false`), and every tool result passes `Redactor` before it becomes a message. Proven by `engine_tests.rs` (`no_secret_reaches_any_provider_request`: a full scripted turn with an `.env` value, a literal model key and a `settings_secret` view, none of which occurs in any recorded request, including a provider error echoing a key), `rejecting_writes_no_value` (a rejected `add_env_var` plus `set_env_value` card leaves `.env` without the variable), and `dispatch_tests.rs` per tool. An MCP tool result is redacted too, including the literal values of `mcp_servers.*.env` (`Redactor::new` collects them with no variable name, so they are always redacted; `redact_settings`, hence `settings_read` `values`, replaces a literal env value by `[redacted]` and leaves `${VAR}` references): `dispatch_tests.rs` (`an_mcp_result_echoing_a_literal_mcp_env_value_is_redacted`, `values_read_masks_a_literal_mcp_env_value_and_keeps_a_reference`). Limit: a MCP result is not filtered for injection; the destination binding of row tests is the guard. No log line carries a secret or user text.

A value typed in a card reaches the backend only as `values` of `settings_agent_apply`; it is never in the proposal payload, the `Proposal`, the `Session` or a tool result. The change-log entry holds the variable name only (the secret effect's `before` and `after` are `null`); the values live in `.env` and in `secret-backups/<entry id>.env` (`services/change_log/DOCS.md`), whose values `Redactor::new` also collects. The applied-card `info` log names the variables, never values.

Redaction of plain values: `Redactor::new` records for each collected value the names it comes from (`.env` pairs and overrides by variable name, referenced variable values by name; literal model keys, backup values and staged values have none). A value is left unredacted only when every source of it is a name listed in `settings.env_vars` with `secret: false`; a value also held by a secret variable, an unlisted `.env` name, an override of another name, a literal key, a backup or a staged value stays redacted. Overrides are attributed to a name only for `.env` keys, listed and referenced names. Accepting that switching a variable to `secret: false` makes its value readable by the agent (see the label of that `update_env_var` row).
